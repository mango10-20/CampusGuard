# CampusGuard——基于深度学习的校园安全事件检测与处置系统

## 1. 项目概述

### 1.1 项目名称

**CampusGuard——基于深度学习的校园安全事件检测与处置系统**

### 1.2 项目概要

CampusGuard是一套基于深度学习与计算机视觉技术的校园安全事件检测与处置系统。系统面向校园固定监控场景，通过分析校园监控视频，对明火、烟雾、人员跌倒、禁区入侵和消防通道车辆占用等可见安全风险进行检测与预警，并将识别结果接入事件复核、任务派发、处置跟踪和结果归档流程，形成完整的校园安全管理闭环，从而提高风险发现和事件处置效率，降低人工持续监控压力。

系统输出定位为“风险预警”或“疑似事件”。算法结果为安保人员提供辅助判断依据，不能替代人工复核、现场核查和管理决策。

### 1.3 项目背景

校园教学楼、实验室、宿舍、走廊、操场、食堂、校门、停车区和消防通道等区域存在火灾、人员跌倒、违规进入和车辆占用等安全风险。传统人工巡检需要安保人员持续查看多路监控画面，工作量大，且容易因疲劳、画面数量多或异常目标较小而造成遗漏。

现有校园监控系统通常侧重视频采集、实时查看和录像回放，风险发现、事件确认、人员调度和结果留痕之间缺少统一衔接。本项目在保留人工管理职责的前提下，引入目标检测、目标跟踪和规则判断技术，辅助发现可见风险，并通过事件管理功能将预警转化为可追踪、可复查、可统计的处置任务。

### 1.4 项目定位与业务闭环

本项目不是单一的图像识别演示，也不以模型代替人工判断，而是覆盖“识别—复核—处置—归档”的校园安全管理平台。核心业务闭环为：

> **事件发现 → 自动预警 → 人工复核 → 任务派发 → 现场处置 → 结果反馈 → 复查归档**

其中，模型负责提供目标检测结果，跟踪与规则模块负责结合区域、时间、轨迹和持续时长生成疑似事件，管理人员负责复核事件并组织后续处置。

### 1.5 建设目标

- 建立面向固定摄像头的分场景视频分析能力，优先覆盖明火、烟雾、人员跌倒、禁区入侵、车辆违停和消防通道车辆占用。
- 采用“通用目标检测模型＋校园安全专项检测模型＋规则判断”的技术架构，避免将所有业务事件混合训练为单一类别模型。
- 支持本地视频、模拟实时视频流和授权摄像头视频接入，并按摄像头场景配置模型、区域和阈值。
- 实现预警截图、事件视频片段、实时通知、人工复核、任务派发、处置跟踪、结果反馈、复查和归档。
- 提供事件查询、统计分析、风险趋势展示和巡检报告导出能力。
- 建立误报反馈、困难样本沉淀和模型版本管理机制，为后续迭代提供依据。

### 1.6 建设原则

- **人机协同**：算法只生成风险预警或疑似事件，关键结论由人工复核。
- **场景适配**：根据摄像头位置选择模型和规则，减少无效计算与误报。
- **规则可配置**：电子围栏、检测时段、持续时间、置信度和冷却时间可按场景调整。
- **过程可追溯**：保留预警依据、复核结论、派发记录、处置反馈和操作日志。
- **先核心后扩展**：首版完成高价值、可验证的检测与处置闭环，再研究复杂行为分析。

## 2. 需求分析

### 2.1 业务需求

系统需要解决以下问题：

1. 多路监控依赖人工持续查看，风险发现效率不稳定。
2. 单帧模型结果容易受光照、遮挡和相似背景影响，需要通过跟踪和时序规则降低误报。
3. 发现风险后缺少统一的人工复核、任务派发、进度跟踪和结果归档流程。
4. 不同区域的风险类型和管理规则不同，需要支持按摄像头、区域和时段灵活配置。
5. 缺少可量化的运行数据，难以评估误报、漏报、响应时长和闭环完成情况。

### 2.2 用户角色

#### 系统管理员

- 管理用户、角色和权限。
- 管理摄像头、检测区域、规则、模型版本和检测阈值。
- 查看全部疑似事件、处置任务、统计报表和系统日志。
- 维护数据存储期限、通知方式和系统基础配置。

#### 复核与调度人员

- 查看实时监控、事件截图、视频片段和算法依据。
- 将疑似事件确认为有效事件或标记为误报。
- 设置事件等级并派发处置任务。
- 跟踪任务进度，审核处置反馈并完成复查归档。

#### 现场处置人员

- 接收被派发的处置任务。
- 更新任务状态和处理进度。
- 填写处置说明，上传现场图片或其他结果材料。
- 在需要补充处理时接收退回意见。

#### 普通查看人员

- 查看授权区域的监控画面、事件记录和统计信息。
- 无权修改算法配置、复核关键事件或变更任务结果。

### 2.3 典型使用场景

- 实验室画面连续出现烟雾，系统生成疑似烟雾事件，复核人员确认后派发任务，现场人员排查并反馈结果。
- 夜间人员进入管理员绘制的楼顶警戒区域并持续超过阈值，系统生成禁区入侵预警。
- 宿舍走廊出现疑似倒地人员，专项模型和连续帧规则完成二次确认，安保人员通过事件页面查看并处置。
- 车辆进入消防通道区域并基本静止，持续超过设定时长后生成疑似占用预警；车辆离开后系统结束事件并停止重复告警。

## 3. 功能范围

### 3.1 首版核心功能

首版围绕可实现、可测试的风险检测与处置闭环建设，核心功能如下：

1. 明火与烟雾检测。
2. 人员跌倒预警。
3. 禁区入侵预警。
4. 车辆违停预警。
5. 消防通道车辆占用预警。
6. 事件人工复核。
7. 处置任务派发与跟踪。
8. 处置结果反馈和归档。
9. 事件统计与可视化。

“重点区域人数超限预警”可作为首版辅助功能或第二阶段功能。该功能仅根据指定区域内的人数阈值、持续时间和允许聚集时段生成预警，不对人群行为性质或意图作自动判断。

### 3.2 最小可行版本

若项目周期或硬件资源有限，最小可行版本应至少打通以下链路：

- 用户登录与基础权限控制。
- 摄像头或本地视频管理。
- 明火、烟雾、`fallen_person`专项目标检测。
- 人员和车辆通用目标检测。
- 禁区、禁停区和消防通道区域绘制。
- 多帧确认、持续时间判断和事件去重。
- 疑似事件生成、人工复核、任务派发、结果反馈和归档。
- 基础事件统计图表。

### 3.3 后续扩展功能

以下功能需要更多真实数据、人体姿态或视频时序模型，误报风险较高，不作为首版已经成熟实现的能力：

- 翻越围栏识别。
- 打架行为识别。
- 追逐行为识别。
- 泛化的异常人员聚集识别。
- 复杂行为语义理解。
- 夜间异常徘徊分析。
- 安全帽、护目镜等防护装备检测。
- 校园道路积水或障碍物检测。
- 温度、烟感等传感器数据融合。

后续研究可结合YOLO-Pose、人体关键点、目标跟踪、动作识别模型和连续视频时序分析，并通过足量真实校园数据进行验证。系统不得将复杂行为或人员意图简单描述为YOLO模型能够直接理解。

## 4. “双模型＋规则判断”算法架构

### 4.1 架构说明

系统不将明火、烟雾、跌倒、违停、入侵和人员聚集全部训练为一个YOLO模型，也不把违停、入侵、人员聚集、消防通道占用等业务事件直接设置为YOLO类别。整体采用三层判断方式：

| 层级 | 主要职责 | 主要输出 |
| --- | --- | --- |
| 通用目标检测模型 | 检测常见人员与车辆目标 | 类别、检测框、置信度 |
| 校园安全专项检测模型 | 检测火焰、烟雾和疑似倒地人员 | 类别、检测框、置信度 |
| 跟踪与规则判断模块 | 结合区域、时间、轨迹、状态和持续时长判断事件 | 风险预警或疑似事件 |

这种设计便于复用成熟预训练权重，也能将“画面中有什么”与“是否满足业务事件条件”分开，降低数据准备难度并提高规则可解释性。

### 4.2 通用目标检测模型

使用YOLO通用预训练模型检测常见目标，主要类别包括：

- `person`
- `car`
- `bus`
- `truck`
- `motorcycle`
- `bicycle`

人员和车辆已有较成熟的公开预训练数据。项目初期优先直接使用预训练权重，在本校固定监控画面中完成分摄像头测试；只有在夜间、远距离、严重遮挡、小目标或特殊俯视角度下效果不足时，才使用校园数据进行微调，不从零开始训练通用模型。

### 4.3 校园安全专项检测模型

使用自行整理和标注的数据集训练或微调专项YOLO模型，主要类别为：

- `fire`
- `smoke`
- `fallen_person`

明火、烟雾和疑似倒地人员具有明显的校园场景适配需求，应重点准备真实或接近真实校园监控视角的数据。首版可使用 `fallen_person` 目标检测实现人员跌倒原型，但该结果只能表示“疑似倒地人员”。为提高跌倒识别精度，后续可结合YOLO-Pose、人体关键点、目标跟踪以及站立到倒地的连续帧状态变化进行判断。

### 4.4 目标跟踪

目标跟踪可采用ByteTrack或同类算法，为同一人员或车辆分配持续编号，辅助实现：

- 记录目标进入和离开区域的时间。
- 计算停留时长、移动距离和近似速度。
- 判断车辆是否基本静止。
- 统计指定区域内的人数。
- 合并同一目标产生的连续检测结果。
- 防止同一事件在每一帧重复告警。

### 4.5 规则判断模块

YOLO负责检测画面中的目标，规则模块根据区域、时间、轨迹、持续时长和连续帧结果决定是否生成事件。

| 规则类型 | 判断逻辑 |
| --- | --- |
| 禁区入侵预警 | 检测到人员进入管理员预先绘制的警戒区域，并持续达到设定时间后触发 |
| 重点区域人数超限预警 | 统计指定区域内人数，结合人数阈值、持续时间和允许聚集时段触发 |
| 车辆违停预警 | 车辆进入禁停区域后，结合目标跟踪、位置变化、静止状态和停留时间判断 |
| 消防通道车辆占用预警 | 车辆与预设消防通道区域有效重叠，并持续超过设定时间后触发 |
| 明火与烟雾预警 | 专项模型连续多帧检测到明火或烟雾后触发，过滤单帧结果 |
| 人员跌倒预警 | 检测到 `fallen_person`，并通过连续多帧或持续时间进行二次确认 |

规则参数应按摄像头独立配置，至少包括检测区域、生效时段、目标类别、置信度阈值、连续确认帧数、持续时间、静止阈值、事件冷却时间和告警等级。

### 4.6 按场景调用模型

不同摄像头不必运行全部模型：

- 停车区和消防通道摄像头重点运行车辆检测、目标跟踪和占用规则。
- 宿舍和走廊摄像头重点运行人员检测、跌倒专项检测和禁区入侵规则。
- 实验室、食堂和配电房等重点区域可运行人员检测、烟火专项检测和禁区规则。
- 校门或操场可根据需要启用人员统计，但只生成基于阈值和时段的预警。

通过按场景加载模型、调整视频抽帧频率和关闭无关规则，可减少无效计算和误报。若后期部署算力有限，可在数据量充足、标签规范统一并完成对比实验后，评估将部分目标合并到一个多类别模型；该方案不作为首版默认架构。

## 5. 核心事件检测方案

### 5.1 明火与烟雾预警

#### 适用区域

食堂、宿舍、实验室、图书馆、停车棚和配电房等区域。

#### 判断流程

1. 专项模型检测 `fire` 和 `smoke`。
2. 保存连续帧中的类别、检测框、置信度和面积变化。
3. 对仅在少量单帧出现的结果进行过滤。
4. 当连续帧数、平均置信度或持续时长达到阈值时生成疑似事件。
5. 根据风险区域、目标面积和持续时间辅助确定预警等级。
6. 保存截图和事件前后视频片段，进入人工复核流程。

云雾、灯光、阳光反射、白色物体和蒸汽等是重点困难负样本。面积扩张速度可以作为辅助特征，但不能单独作为火灾结论。

### 5.2 人员跌倒预警

#### 适用区域

操场、体育馆、宿舍楼道、教学楼、楼梯间等区域。

#### 首版方案

1. 专项模型检测 `fallen_person`。
2. 对同一位置或同一跟踪目标进行连续多帧确认。
3. 当疑似倒地状态持续超过阈值时生成预警。
4. 保存事件截图和视频片段，由人工复核是否属于真实跌倒。

正常躺卧、弯腰、坐地和体育活动可能产生相似外观，因此首版不得将单帧检测结果直接认定为真实跌倒。

#### 后续增强方案

可在通用人员检测和跟踪基础上，引入YOLO-Pose或其他姿态估计模型，综合人体关键点角度、检测框宽高比、重心下降速度、姿态转换过程和倒地后持续时间，提高识别精度。

### 5.3 禁区入侵预警

#### 适用区域

实验室、机房、楼顶、施工区域、危险设备周围和夜间教学楼等区域。

#### 判断流程

1. 管理员在固定摄像头画面中绘制多边形警戒区域。
2. 通用模型检测 `person`，跟踪算法分配目标编号。
3. 使用人体检测框底部中心点或设定的重叠比例判断目标是否进入区域。
4. 检查当前时间是否属于规则生效时段。
5. 记录进入时间，持续达到阈值后生成疑似入侵事件。
6. 人员离开后结束事件，并通过冷却时间避免重复告警。

人员只在禁区边缘经过、检测框轻微抖动或短时进入时，不应立即产生事件。

### 5.4 车辆违停预警

#### 适用区域

校门、校园道路、教学楼出入口、禁停区和应急通道周边。

#### 判断流程

1. 管理员绘制禁停多边形区域并设置生效时段。
2. 通用模型检测 `car`、`bus`、`truck`、`motorcycle` 和 `bicycle` 等目标。
3. 目标跟踪算法记录同一车辆的位置变化和停留时长。
4. 车辆进入区域后，结合中心点移动距离、轨迹速度或检测框变化判断是否基本静止。
5. 静止且停留超过阈值后生成疑似违停预警。
6. 车辆离开或持续运动时结束判断，不将正常驶过直接认定为违停。

### 5.5 消防通道车辆占用预警

系统不训练名为“消防通道占用”的YOLO类别。消防通道占用属于车辆检测结果与固定区域、运动状态和持续时间组合形成的业务事件，具体流程如下：

1. 管理员在固定摄像头画面中绘制消防通道多边形区域。
2. 通用YOLO模型检测车辆。
3. 目标跟踪算法持续跟踪同一车辆。
4. 判断车辆底部中心点或检测框与消防通道区域的重叠关系。
5. 根据连续帧的位置变化判断车辆是否基本静止。
6. 当有效重叠、静止状态和占用持续时间均超过阈值时，生成疑似占用预警。
7. 保存事件截图、摄像头、发生时间、车辆位置和持续时长等信息。
8. 事件进入人工复核和任务处置流程。
9. 车辆离开后结束事件，并记录结束时间，防止同一事件重复告警。

车辆正常驶过、临时停靠和持续占用必须通过运动状态与时间阈值加以区分。针对救援车辆、授权施工车辆等特殊情况，可配置白名单时段或由人工复核排除。

### 5.6 重点区域人数超限预警  ==（不一定做）==

该功能作为辅助功能或第二阶段功能：

1. 使用通用模型检测并跟踪区域内的 `person`。
2. 按底部中心点是否位于区域内统计人数。
3. 结合人数阈值、持续时间、生效时段和允许聚集时段生成预警。
4. 通过目标编号去重，降低遮挡和重复计数影响。

该功能只反映“指定区域内人数持续超过配置阈值”，不对排队、集合、上下学等人群行为是否异常作语义判断。

## 6. 系统总体架构与技术流程

### 6.1 总体架构

```text
摄像头 / 本地视频 / 模拟实时视频流
                    │
                    ▼
             视频接入与预处理层
          解码、抽帧、缩放、场景配置
                    │
                    ▼
┌────────────────────────────────────┐
│             视觉分析层             │
│ 通用YOLO模型 │ 专项YOLO模型 │ 目标跟踪 │
└────────────────────────────────────┘
                    │
                    ▼
┌────────────────────────────────────┐
│             规则判断层             │
│ 区域关系 │ 时段 │ 持续时间 │ 静止状态 │
│ 多帧确认 │ 事件合并 │ 冷却时间 │ 分级 │
└────────────────────────────────────┘
                    │
                    ▼
              疑似事件管理中心
                    │
                    ▼
    人工复核 → 任务派发 → 现场处置
                    │
                    ▼
          结果反馈 → 复查 → 归档
                    │
                    ▼
            查询、统计与巡检报告
```

系统分为五个层次：

1. **视频接入层**：读取授权摄像头、视频文件或模拟实时视频流。
2. **算法分析层**：完成通用目标检测、专项检测、目标跟踪和结果结构化。
3. **规则判断层**：将帧级结果转换为可解释的疑似事件，并完成多帧确认、去重和分级。
4. **业务服务层**：负责用户权限、人工复核、任务派发、处置反馈、归档和报表。
5. **应用展示层**：提供实时监控、事件中心、任务中心、统计页面和配置界面。

### 6.2 系统技术流程

> **监控视频接入 → 视频抽帧与预处理 → 按场景调用相应模型 → 目标检测 → 目标跟踪 → 区域与时间规则判断 → 事件生成 → 人工复核 → 任务派发 → 处置反馈 → 复查归档 → 数据统计**

### 6.3 事件状态流转

```text
疑似事件 / 待复核
        ├── 复核无效 → 误报归档 → 困难样本候选
        └── 复核有效 → 待派发 → 待接收 → 处理中
                                      │
                                      ▼
                               已反馈 / 待复查
                                ├── 退回补充处理
                                └── 复查通过 → 已归档
```

所有状态变化均记录操作人、时间、意见和相关附件。模型置信度只作为复核依据之一，不直接决定最终事件结论。

### 6.4 事件去重与结束机制

同一摄像头、同一目标、同一事件类型在短时间内连续出现时，应合并为一条事件。可综合以下条件生成事件键：

```text
摄像头编号 + 规则编号 + 事件类型 + 跟踪目标编号
```

对于火焰、烟雾等难以稳定分配跟踪编号的目标，可结合区域位置、检测框重叠率和时间间隔进行合并。目标离开、风险状态消失达到恢复阈值或管理员确认结束后，事件进入结束或处置阶段；在冷却时间内不重复创建同类事件。

## 7. 系统功能模块

### 7.1 用户、角色与权限管理

- 用户登录、退出和密码安全存储。
- 用户、角色、菜单和操作权限管理。
- 按校园区域或摄像头限制数据访问范围。
- 对模型配置、事件复核、任务派发和归档等关键操作进行权限校验。

### 7.2 摄像头和检测区域管理

- 添加、修改、停用和查询摄像头。
- 配置摄像头名称、位置、视频地址和在线状态。
- 在固定画面上绘制禁区、禁停区、消防通道区和人数统计区等多边形区域。
- 为不同摄像头启用不同模型、规则和抽帧频率。
- 支持本地视频循环播放或模拟实时视频流用于开发演示。

### 7.3 实时监控与检测结果展示

- 以宫格形式展示多路授权监控画面。
- 显示目标框、类别、跟踪编号和置信度。
- 显示摄像头状态、模型运行状态和当前启用规则。
- 在原始画面和算法分析画面之间切换。
- 点击预警后定位到对应摄像头和异常时刻。

### 7.4 模型版本与检测阈值配置

- 管理通用模型和专项模型的版本、类别、文件位置、启用状态和评价结果。
- 按摄像头配置置信度阈值、连续确认帧数、持续时间、静止阈值和抽帧频率。
- 保留模型或规则配置变更记录，支持回溯事件产生时使用的版本。
- 新模型上线前先在离线测试集和试运行摄像头中评估。

### 7.5 事件预警与人工复核

- 通过页面提示、声音和WebSocket推送新预警。
- 展示事件类型、摄像头、位置、发生时间、持续时长、截图、视频片段、检测框和模型置信度。
- 支持确认有效、标记误报、调整事件等级和填写复核说明。
- 高等级事件突出显示；邮件、短信或校园消息平台作为可选通知渠道。

### 7.6 处置任务派发与进度跟踪

- 将复核有效的事件派发给指定处置人员或部门。
- 设置优先级、要求完成时间和处置说明。
- 记录任务接收、开始处理、延期、转派和完成状态。
- 对超时未接收或未完成任务进行提示。

### 7.7 现场反馈、复查与归档

- 现场人员填写处置说明并上传图片或相关材料。
- 复查人员查看处置结果，可通过或退回补充处理。
- 复查通过后归档事件，并保留完整时间线。
- 误报事件可进入困难样本候选库，经脱敏和审核后用于模型迭代。

### 7.8 事件查询、统计和可视化

- 按时间、区域、摄像头、事件类型、等级、状态和负责人查询。
- 展示事件总数、各类事件占比、时间趋势、区域排行和高发时段。
- 展示人工复核通过率、平均响应时间、闭环完成率、误报次数和摄像头在线率。
- 按日、周或月生成巡检报告，支持导出PDF。

### 7.9 系统日志与操作记录

- 用户登录和访问日志。
- 摄像头、区域、规则、模型和阈值配置变更日志。
- 事件复核、任务派发、状态变更、结果反馈和归档日志。
- 视频读取失败、算法服务异常和系统运行错误日志。

## 8. 技术选型与部署方案

### 8.1 前端技术

- **Vue 3**：构建管理端页面。
- **Element Plus**：实现表单、表格、弹窗和后台管理组件。
- **ECharts**：实现事件趋势、类型占比和区域排行等图表。
- **Canvas或SVG**：实现固定画面中的多边形检测区域绘制。
- **WebSocket**：接收实时预警、任务变化和摄像头状态。

### 8.2 后端技术

可根据团队能力选择以下方案：

#### 方案A：统一使用Python

- 使用FastAPI提供业务接口和算法接口。
- 适合团队普遍熟悉Python、开发周期较短的情况。

#### 方案B：业务服务与算法服务分离

- Spring Boot负责用户、权限、摄像头、规则、事件、任务和报表等业务。
- Python/FastAPI负责模型推理、目标跟踪和规则计算服务。
- 两类服务通过HTTP接口或消息队列传递结构化结果。

方案B分层更清楚，适合具备Java开发能力和多人协作的团队；课程项目应根据人力选择，避免为追求架构复杂度影响核心闭环完成。

### 8.3 算法与视频技术

- Python、PyTorch、YOLO系列模型和OpenCV。
- ByteTrack或同类多目标跟踪算法。
- YOLO-Pose或其他人体姿态估计模型作为跌倒识别后续增强。
- FFmpeg用于视频解码、转码、抽帧和事件片段截取。
- FastAPI提供算法推理接口。

算法服务返回目标类别、检测框、置信度、跟踪编号、时间戳和规则结果等结构化数据，不直接处理用户权限，也不绕过业务服务修改事件最终结论。

### 8.4 数据与通信

- **MySQL**：保存用户、摄像头、区域、规则、事件、任务、反馈和日志。
- **Redis**：缓存摄像头状态、短期轨迹、规则计时器和事件去重信息。
- **WebSocket**：实时推送预警和任务状态。
- **本地文件系统或对象存储**：保存事件截图、视频片段和处置附件。

### 8.5 部署方式

- GPU计算机运行算法推理服务；无GPU时可降低输入尺寸和抽帧频率进行演示。
- 普通计算机运行前端、业务后端、MySQL和Redis。
- 使用Docker Compose统一管理服务。
- 在没有专用服务器时，可在一台高性能计算机或校园局域网内完成部署。
- 生产或真实试点环境应限制摄像头网络访问，分离原始视频与业务数据访问权限。

## 9. 数据集规划与模型训练

### 9.1 通用公开数据

人员和车辆等常见目标优先使用YOLO公开预训练权重，无需重新收集大规模通用数据。项目应先针对各类校园摄像头进行基线测试，记录白天、夜间、远距离、遮挡和特殊视角下的检测效果；只有效果不足时，才补充校园样本进行微调。

### 9.2 校园专项数据

专项数据重点收集和标注明火、烟雾、人员跌倒，并覆盖：

- 教室、宿舍、走廊、实验室、食堂、操场和校门等场景。
- 白天、夜间、阴影、逆光和低照度。
- 远距离、小目标和不同摄像头角度。
- 不同程度的遮挡。
- 室内与室外场景。
- 容易误判的相似目标和复杂背景。

真实异常事件较少时，可综合使用公开数据、合规网络公开视频和小组模拟采集数据，但独立测试必须包含真实校园监控视角或尽可能接近实际部署条件的校园场景。

### 9.3 负样本与困难样本

数据集必须包含没有安全事件的正常监控画面，以及容易产生误报的画面，例如：

- 云雾、灯光、阳光反射、蒸汽和白色物体。
- 正常躺卧、弯腰、坐地和体育活动。
- 车辆正常经过和短暂停靠。
- 人员经过禁区边缘但未真正进入。
- 食堂排队、操场集合和上下学等正常人群场景。

人工复核为误报的样本可经脱敏、筛选和重新标注后加入困难样本库，但不得未经审核直接作为训练标签。

### 9.4 数据标注规范

- 专项检测类别统一为 `fire`、`smoke`、`fallen_person`。
- 标注框应完整、紧密地覆盖可见目标；严重遮挡或无法确认的样本按统一规则处理。
- 同步记录数据来源、摄像头或场景编号、光照条件、遮挡情况、标注人员和复核人员。
- 建立抽检与复核机制，处理漏标、错标、框偏移和类别不一致问题。
- 数据集保持类别和场景相对平衡，避免烟雾或跌倒等稀有类别样本过少。

### 9.5 数据集划分

可采用训练集70%、验证集15%、测试集15%的参考比例，但必须按摄像头、场景或完整视频划分，不能把同一视频的相邻帧随机分到不同集合。相邻帧高度相似，混入不同集合会造成数据泄漏并导致测试指标虚高。

测试集在训练和调参阶段应保持独立，最终同时报告不同摄像头、光照、距离和遮挡条件下的结果。

### 9.6 数据增强

- 亮度、对比度、色温和低照度变化。
- 模糊、噪声和压缩失真。
- 合理的缩放、裁剪和水平翻转。
- 随机遮挡以及适合目标检测的组合增强。
- 有控制地模拟雨、雾等环境效果。

数据增强应保持事件语义和检测框有效，不能用不符合固定监控视角的过度变换代替真实数据。

### 9.7 训练与版本管理

1. 使用预训练权重作为起点，对专项模型进行迁移学习或微调。
2. 记录训练数据版本、配置、随机种子、权重文件和评价结果。
3. 通过验证集选择参数，通过独立测试集进行最终评价。
4. 新模型与当前模型进行离线对比和有限摄像头试运行。
5. 上线模型关联版本号，发生误报或漏报时能够回溯。

## 10. 规则配置与事件生成设计

### 10.1 通用规则结构

一条检测规则可由以下配置组成：

```text
摄像头 + 场景类型 + 模型版本 + 目标类别 + 多边形区域
+ 生效时段 + 置信度阈值 + 连续确认帧数 + 持续时间
+ 静止或移动阈值 + 事件冷却时间 + 预警等级
```

### 10.2 区域关系判断

- 人员进入区域可优先使用人体检测框底部中心点，降低检测框上半部分跨界造成的误判。
- 车辆占用可使用车辆底部中心点、检测框与区域的交并比例，或两者组合。
- 对警戒线边缘设置适当缓冲带和进入/离开迟滞阈值，减少检测框抖动造成的频繁状态切换。

### 10.3 时序确认

- 明火、烟雾和 `fallen_person` 使用连续帧数或持续时间确认。
- 入侵、违停和消防通道占用使用跟踪目标的进入时间、停留时长和运动状态确认。
- 风险短暂消失时可设置容忍帧数，避免遮挡导致同一事件被拆分。
- 事件结束后设置冷却时间，避免目标在边界附近反复触发。

### 10.4 预警等级

预警等级可以综合事件类型、区域重要程度、持续时长、目标规模和模型置信度配置。等级用于通知和处置优先级排序，不代表算法已确认事件真实发生；最终结论仍以人工复核和现场反馈为准。

## 12. 接口与服务协作设计

### 12.1 视频与算法接口

- 视频接入模块向算法服务提供带摄像头编号和时间戳的视频帧。
- 算法服务返回模型版本、目标类别、检测框、置信度和跟踪编号等结果。
- 规则模块根据摄像头配置读取区域与阈值，生成或更新疑似事件。
- 事件截图和视频片段保存成功后，业务服务写入媒体索引。

### 12.2 业务接口

- 用户、角色和权限接口。
- 摄像头、检测区域和检测规则接口。
- 模型版本和算法配置接口。
- 疑似事件查询、复核和误报标记接口。
- 处置任务派发、接收、进度更新和反馈接口。
- 复查、退回和归档接口。
- 统计报表和日志查询接口。

### 12.3 实时通信

WebSocket用于推送新预警、复核结果、任务派发、任务超时和摄像头状态变化。客户端断线重连后应通过普通接口补取未读事件，避免只依赖实时消息造成数据遗漏。

---

## 13. 非功能性要求

### 13.1 性能要求

- 课程演示环境下优先保证2～4路视频稳定运行，并记录实际硬件配置。
- 告警生成延迟目标可设为3秒以内，但应结合抽帧频率、连续确认时间和硬件实测说明。
- 支持通过输入尺寸、抽帧频率和按场景加载模型平衡速度与精度。
- 视频分析、业务接口和媒体存储解耦，避免单个慢任务阻塞全部摄像头。

### 13.2 稳定性要求

- 摄像头断开后显示离线状态，并按策略尝试恢复。
- 算法服务异常时不影响历史事件查询和已派发任务处理。
- 视频读取失败、模型加载失败和消息推送失败均记录日志。
- 使用事件去重、结束和冷却机制控制数据库增长。

### 13.3 安全与隐私要求

- 明确摄像头接入权限，不向未授权用户展示监控区域。
- 用户密码安全存储，关键接口进行身份认证和权限校验。
- 对用于训练、展示和报告的图片进行必要脱敏，限制无关人员信息传播。
- 为原始视频、事件截图、处置附件和日志设置访问控制与存储期限。
- 记录查看、下载、修改和删除等关键操作。
- 数据采集、使用和保留遵循学校管理制度及适用的个人信息和数据安全要求。

### 13.4 可维护性要求

- 模型、规则和业务服务边界清楚，可单独升级。
- 配置项具有默认值、取值范围和修改日志。
- 核心接口提供异常处理和基本测试。
- 项目提供启动说明、部署文档、接口文档和测试报告。

- 第1周：完成阶段1～2。
- 第2～3周：完成数据初版、通用模型基线和系统基础模块。

## 16. 评价指标与测试方案

### 16.1 模型指标

- Precision。
- Recall。
- F1-score。
- mAP@0.5和mAP@0.5:0.95。
- 单帧推理延迟。
- 视频处理帧率FPS。
- 不同目标尺寸、光照、遮挡和摄像头视角下的分类结果。

### 16.2 系统运行指标

- 每个摄像头每天的误报次数。
- 事件漏报率。
- 事件发现延迟。
- 告警生成时间。
- 同一事件重复告警次数。
- 人工复核通过率。
- 处置任务响应时间。
- 事件闭环完成率。
- 不同光照和摄像头场景下的稳定性。
- 多路视频并发处理能力和长时间运行稳定性。

### 16.3 指标统计原则

- 以完整事件而非单帧作为业务评价单位。
- 明确事件开始、发现、告警、复核、派发、接收、反馈和归档时间点。
- 按摄像头、场景、事件类型和光照条件分别统计，不只给出总体平均值。
- 同时报告有效预警、误报、漏报、重复告警和人工复核结果。
- mAP只能说明检测模型表现，不能单独证明整个系统有效；最终效果还取决于目标跟踪、区域规则、阈值设置、事件去重和处置流程。

### 16.4 测试内容

- 正常样本、异常样本和困难样本测试。
- 日间、夜间、逆光、低照度、远距离和遮挡测试。
- 正常驶过、短暂停靠、持续违停和消防通道占用对比测试。
- 禁区边缘经过、短暂进入和持续进入对比测试。
- 单帧误检、多帧确认、遮挡恢复和事件冷却测试。
- 摄像头断开、算法服务异常、消息断线重连和任务状态流转测试。

## 17. 主要风险与应对措施

| 风险 | 可能影响 | 应对措施 |
| --- | --- | --- |
| 真实异常事件数据少 | 专项模型泛化能力不足 | 使用公开数据、合规模拟采集和困难样本补充；独立测试必须包含真实或接近真实的校园场景 |
| 夜间和远距离识别下降 | 小目标漏检、置信度降低 | 补充低照度、小目标数据，按摄像头调整阈值、输入尺寸和抽帧频率 |
| 遮挡造成漏检或目标编号变化 | 事件中断、计时不准 | 结合目标跟踪、连续帧判断、短时丢失容忍和区域状态缓存 |
| 单帧误报 | 无效预警过多 | 使用多帧确认、置信度阈值、持续时间和事件冷却时间 |
| 正常行为被误判 | 人工负担增加 | 使用区域、时段、持续时长和人工复核；增加正常躺卧、排队、短暂停车等困难负样本 |
| 车辆正常驶过被判断为占用 | 消防通道误报 | 结合区域重叠、移动速度、静止状态和停留阈值，并在离开后结束事件 |
| 算力不足 | 多路视频卡顿、延迟升高 | 不同摄像头按需加载模型，调整抽帧频率、输入尺寸和模型规模 |
| 摄像头视角变化 | 原区域坐标和阈值失效 | 摄像头移动后要求重新标定检测区域并进行场景测试 |
| 隐私与数据安全风险 | 数据泄露或越权访问 | 明确摄像头权限、数据脱敏、访问控制、存储期限和操作日志 |
| 没有真实摄像头接口 | 无法完成实时演示 | 使用本地视频循环播放或模拟实时流，并在报告中说明数据来源和限制 |
| 功能范围过大 | 无法按期形成闭环 | 优先完成首版核心事件与处置流程，复杂行为移至后续研究 |
| 演示设备或网络异常 | 答辩流程中断 | 准备本地部署、固定测试视频、截图和录屏备用方案 |

## 18. 项目创新点

### 18.1 双模型与业务规则解耦

复用通用预训练模型检测人员和车辆，专项模型聚焦火焰、烟雾和疑似倒地人员，再通过可配置规则形成事件，兼顾数据成本、可解释性和场景适配能力。

### 18.2 时空联合判断

系统不把单帧检测直接等同于真实事件，而是结合目标轨迹、区域关系、移动状态、持续时间和连续帧结果生成预警，降低单帧误判。

### 18.3 从预警到处置的完整闭环

系统覆盖事件发现、自动预警、人工复核、任务派发、现场处置、结果反馈、复查归档和统计分析，能够展示算法与校园安全业务的完整结合。

### 18.4 人工反馈驱动迭代

误报标记和复核意见可沉淀为困难样本候选，结合模型版本和规则配置记录定位问题，为后续数据补充、模型微调和阈值优化提供依据。

## 19. 答辩演示方案

建议准备包含明火或烟雾、疑似跌倒、禁区入侵、车辆违停和消防通道占用的分段模拟校园监控视频，并按以下流程展示：

1. 管理员登录并查看系统概况。
2. 展示摄像头列表、场景类型及按需启用的模型。
3. 在固定画面中绘制禁区、禁停区或消防通道区域并配置阈值。
4. 开启视频分析，展示通用模型、专项模型和跟踪编号。
5. 人员进入禁区并持续超过阈值后，系统生成疑似入侵预警。
6. 出现 `fallen_person` 或烟火目标时，系统经连续多帧确认后生成预警。
7. 车辆正常驶过消防通道时不生成占用事件；车辆静止并超过阈值后生成疑似占用预警。
8. 复核人员查看截图、视频和规则依据，将有效事件派发给现场人员。
9. 现场人员更新进度并上传处置结果，复查人员审核并归档。
10. 展示事件统计、响应时间、人工复核通过率和闭环完成率，并导出巡检报告。

演示中应同时展示正常样本和困难样本，说明系统的适用条件、误报控制方法以及人工复核的必要性。

## 20. 项目验收标准

### 20.1 功能验收

- 能够正常登录并区分用户、角色和数据权限。
- 能够添加视频源、配置摄像头场景并显示分析画面。
- 能够分别调用通用模型和校园安全专项模型。
- 能够配置电子围栏、禁停区、消防通道区和时序规则。
- 能够对首版核心风险生成预警，并展示截图、视频和规则依据。
- 能够完成人工复核、任务派发、进度跟踪、结果反馈、复查和归档。
- 能够查询事件、查看统计数据和导出巡检报告。
- 能够查看模型版本、阈值配置和关键操作日志。

### 20.2 算法与规则验收

- 提供独立测试集、数据划分说明和模型评价指标。
- 展示正常样本、异常样本、负样本和困难样本结果。
- 提供通用预训练模型的校园场景基线测试。
- 提供专项模型训练或微调记录及版本信息。
- 验证多帧确认、区域判断、停留时间、静止状态、事件去重和冷却机制。
- 统计每个摄像头每天误报次数、事件漏报率、告警延迟和重复告警次数。

### 20.3 工程验收

- 前端、业务后端、算法服务、数据库和实时消息能够完整联调。
- 系统能够连续运行完整演示流程，摄像头或服务异常时有明确提示和日志。
- 项目具有启动说明、部署文档、接口文档、数据库说明和测试报告。
- 核心接口具有基本异常处理，关键业务状态可追溯。

### 20.4 首版验收边界

首版验收重点是可见目标的检测、可配置规则生成预警以及事件处置闭环，不要求系统自动理解打架、追逐、翻越等复杂行为意图，也不以单一mAP指标代替系统运行效果评价。

## 21. 后续迭代方向

- 结合YOLO-Pose、人体关键点和时序状态机提高跌倒识别精度。
- 通过困难样本和真实校园数据持续微调专项模型。
- 引入更稳健的跨遮挡目标跟踪和小目标检测方案。
- 在充分采集真实数据后研究动作识别和复杂行为时序分析。
- 评估边缘设备部署、模型量化和多路视频调度。
- 在合规前提下接入烟感、温度或门禁信息，进行多源风险辅助验证。

CampusGuard的建设重点是以可解释的视觉检测和规则判断辅助校园风险发现，并通过人工复核与任务处置机制形成可靠、可追溯的安全管理闭环。
